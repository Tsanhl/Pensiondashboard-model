26. V3 AMENDMENT — MEASURE TRAINING DURATION; 48 IS A COMPARATOR, NOT A MAGIC TARGET

This section implements the owner's new request to test whether 48 optimiser updates is a suitable choice. It supersedes any surviving wording that mandates completion or selection of exactly 48 updates. Preserve 0/48 and earlier limits as historical facts, not a present quality guarantee. No evidence in the supplied v2 file establishes why 48 was originally chosen or that it is optimal. Audit the actual original proposal and do not retrospectively invent a rationale.

26.1 Declare what is being compared
Create TRAINING-DURATION-STUDY.json and a readable companion before inspecting new results. Record the parent/base, dataset/splits, formatter/loss/reviewer hashes, optimiser, scheduler, trainable parameters, batch size, accumulation, sampling/packing/drop-last behaviour, seed, candidate checkpoints, early-stop rule and finite resource/inference/review budgets.

The default first study is ONE compatible training trajectory capped at 48 actual optimiser updates, with candidate snapshots at additional-update counts 0, 12, 24, 36 and 48. Point 0 is the intact baseline checkpoint 104, not a different model labelled checkpoint 0. These milestones are a proposed coarse comparison grid, not a claim that they are individually optimal. Preserve the absolute parent identifier separately from each new-run relative update count.

Do NOT run separate 12-, 24-, 36- and 48-step training jobs by default: that would consume 120 updates and four training starts, not the original bounded experiment. One trajectory saves intermediate checkpoints while keeping the rest constant. A shorter snapshot from a schedule designed for a 48-step horizon is not equivalent to a separately trained short-horizon schedule; report that limitation. Comparing different learning-rate schedules, seeds, ranks or datasets is another experiment, not a free extension of this one.

If matching saved checkpoints and exact evaluation receipts already exist, use them instead of retraining. If a completed run saved only step 48, report that earlier comparison evidence is unavailable; do not claim it is best and do not silently launch another full run. A changed cadence, total compute or incomplete compatibility with the old authority requires one consolidated exact amendment request through the existing controls.

The new owner request authorises preparation of this duration study, code instrumentation and PDU50 fixture/evaluator integration plus bounded development inference within existing provider/resource permissions. It does not reset failed full-model probes or enlarge memory/swap/time budgets. Execute training only under valid applicable remaining run authority and a passed compatible two-update proof. If an immutable old approval permits only an exact incompatible configuration, show the specific changed fields once; do not overwrite its signature or repeatedly ask for already documented consent.

26.2 Verify that an update really is an update
Inspect the installed trainer/optimiser and wrappers. Do not blindly equate CLI --iters with completed optimiser updates, especially under gradient accumulation. Track actual completed optimiser-step events and synchronisation; label microsteps, gradient evaluations, training batches, epochs and generation calls separately.

Record for each saved candidate: completed updates, microbatches, sample IDs or privacy-preserving IDs and exposure counts, unique examples seen, total presented prompt tokens, supervised nonpadding target tokens, effective batch, data-order state and exact optimiser/RNG state.

For a simple un-packed single-device run, effective examples per update may be microbatch_size * accumulation_steps, but only when that matches real code, full/partial batches and sampler behaviour. Compute example-exposure equivalents as total example presentations / eligible training-example count, and explicitly state assumptions. Packing, sampling with replacement and repeated/truncated examples require their own accounting. Do not infer '24 examples x two epochs = 48 updates' without runtime evidence. Token volume is a complementary exposure measure, not a universal learning-dose formula.

26.3 Select on the existing validation role, not on the new 50-question exam
Use the compatible reviewed eight-example validation set for teacher-forced loss and a fixed rubric for generated-answer behaviour. Remove target answers from inference inputs. Bind supervised loss and generated answers to the exact saved adapter bytes after loading. Inputs legitimately include their permitted evidence, not hidden expected answers. Label validation replay with supplied evidence as selection diagnostics, not normal-retrieval qualification.

Before scoring, freeze a rule. Suggested default to be ratified through the existing policy process:
1. Invalid identity, partial adapter, resource failure, missing review, or any observed hard safety/privacy/factual/citation-applicability failure makes the checkpoint ineligible for promotion. Operationally unreviewed candidates are UNASSESSED, not evidence of worse legal capability.
2. Among fully assessed hard-gate-clean checkpoints, prefer the larger count of correct, complete or genuinely justified-clarification outcomes on the fixed validation rubric, then fewer material omissions and unnecessary/repeated questions. A blanket refusal cannot win by containing no false claims.
3. Use validation loss as a secondary selection signal, not a replacement for answer semantics. Compare like-for-like token weighting and per-example reports so a long item does not conceal poor performance elsewhere.
4. When semantic outcomes are tied and relative validation loss differs by at most a PREDECLARED 1% tolerance, prefer fewer additional updates and lower demonstrated resource cost. This tolerance is a conservative engineering tie rule, not statistical proof of equal models; pin a different justified tolerance before results only through the documented process.
5. Select baseline 104 or NONE if no new checkpoint shows the required observed benefit without hard regression. There is no obligation to select step 48.

If a meaningful monotonic-regression early stop is already declared, use it without relabelling the run as 48/48. Do not invent a stopping rule from the current trajectory after seeing it. The default coarse comparison assesses scheduled checkpoints through the authorised cap unless a resource/safety guard or declared stopping rule intervenes. If the run stops at 24, steps 36/48 are NOT_RUN; no conclusion comparing those unobserved points is allowed.

The first study's nominal selection workload is at most five candidates x eight validation examples = 40 generated validation answers, plus required loss passes and review calls. Calculate the actual maximum including both reviewer calls, allowed operational retries and runtime/evaluator receipt reuse. Share a review only when job scope and byte bindings legitimately match; do not fabricate credit or add unlimited calls. Pin provider-call/token/time budgets before launch. If current quota does not fit, give the exact missing budget/candidate coverage rather than picking a winner from unassessed checkpoints.

Keep one model copy resident at a time. Checkpoints may be stored during training and evaluated sequentially after releasing training memory if that preserves the fixed schedule and declared selection/stop policy. An inference-only checkpoint can be evaluated without replacing the active user service. Evaluation overhead must fit its own approved budget, not be hidden inside the old training deadline.

26.4 What conclusion is allowed?
Return a table for candidate 0/12/24/36/48: actual exposure, loss, semantic outcomes, hard failures, unnecessary questions, source support, resource peaks, time, exact hashes and eligible/selected/not-run status.

Allowed: 'Among the fully assessed saved checkpoints on this dataset, parent, seed, schedule and limits, step 24 was selected; step 48 was not better under the predeclared rule.'
Not allowed: '24 is universally optimal', '48 is best because it is the last step', or 'the Mac cannot train because a policy guard stopped it.' A single short trajectory and eight validation cases give limited evidence. More than 48 updates, new schedules/seeds or a new dataset requires a distinct reviewed experiment and explicit compute/attempt authority, never an automatic extension.

Rename current status fields to UPDATE_CAP / SCHEDULED_CHECKPOINTS / COMPLETED_MAIN_UPDATES / SELECTED_ADDITIONAL_UPDATE_COUNT / STOP_REASON / DURATION_COMPARISON_SCOPE. Preserve historical UPDATES_OUT_OF_48 fields in archived receipts, not as a mandatory completion target in new summaries.
